# GR00T–GIE Execution Authority Mapping

## Status

**Architecture / source-level mapping — v0.1**  
**Purpose:** define the enforcement boundary for the GR00T humanoid simulation path before implementation.

This document records the source-level mapping used to design the first GIE execution-authority experiment. It deliberately separates verified execution flow from implementation decisions that remain open.

---

## 1. Objective

The experiment tests whether a generated autonomous action is sufficient to acquire execution authority.

The answer is intentionally **no**.

The governing principle is:

> **A valid action generated by GR00T does not constitute authority to execute that action.**

The experiment therefore introduces an independent Governance Invariants Engine (GIE) at the point where a cached policy action is selected for execution.

The GR00T policy remains unchanged and continues inference even when execution authority is revoked.

---

## 2. Source-Level Call Chain

The current closed-loop path is:

```text
policy_runner.rollout_policy()
    |
    +-- actions = policy.get_action(env, obs)
    |
    +-- Gr00tRemoteClosedloopPolicy.get_action()
    |       |
    |       +-- fetch_chunk()
    |       |      +-- _get_action_chunk(...)
    |       |             +-- remote GR00T policy
    |       |
    |       +-- _chunking_state.get_action(
    |              fetch_chunk,
    |              hold_action=_extract_hold_action(observation)
    |          )
    |
    +-- env.step(actions)
            |
            +-- Isaac Lab ActionManager
                    |
                    +-- G1 embodiment action term
                    |      |
                    |      +-- WBC / Pink IK path
                    |             |
                    |             +-- set_joint_position_target(...)
                    |
                    +-- PhysX
```

The critical observation is that the scheduler is the layer that converts a multi-step action chunk into the **single action consumed for the current simulation step**.

This makes the scheduler the natural Point B enforcement location.

---

## 3. Point B and Point C

### Point B — Execution-Authority Enforcement Point

**Location:** immediately after the scheduler extracts the current timestep action from the cached action chunk and before that action is returned to the policy runner.

Conceptually:

```text
current_action_chunk[env_id, current_action_index]
                    |
                    v
             extracted_action
                    |
                    v
              GIE.check()
              /          \
          ALLOW          BLOCK
            |               |
            v               v
   extracted_action     hold_action
            \               /
             \             /
              v           v
                 return action
                       |
                       v
                   env.step()
```

This boundary satisfies the central SIF principle:

> **Authorization must be evaluated at the point where execution becomes consequential.**

### Point C — Physical-Effect / Actuator-Facing Boundary

Downstream of `env.step()`, the action enters the Isaac Lab ActionManager and the embodiment-specific G1 WBC/Pink path, ultimately reaching the actuator-facing call:

```python
self._asset.set_joint_position_target(...)
```

Point C is therefore the useful downstream observation boundary for proving that an unauthorized GR00T action did not reach the physical/simulation control path.

Point B is preferred for enforcement because it is earlier, deterministic, policy-independent, and does not require modifying the embodiment controller.

---

## 4. H1 — Authority Is Not Generated by the Policy

### Hypothesis

> A valid action generated by GR00T does not constitute authority to execute that action.

A GR00T action may be:

- syntactically valid;
- within the expected action space;
- generated by a valid inference request;
- cached inside an action chunk;
- still valid according to the policy itself;

and nevertheless have **no execution authority**.

The GIE therefore evaluates execution authority independently of GR00T validity.

The architectural separation is:

```text
GR00T:
    What action should the humanoid perform?

GIE:
    Does this action currently have authority to execute?
```

The two questions must not be conflated.

---

## 5. H2 — Per-Action Re-Evaluation

### Hypothesis

> Execution authority is evaluated for each action consumed from the chunk, not only when the chunk is received.

`ActionChunkScheduler` maintains a cached chunk and a per-environment action index. During normal replay:

```text
index = 0
index = 1
index = 2
...
index = action_chunk_length - 1
```

A governance decision made only when the chunk is fetched would therefore be insufficient.

Example:

```text
chunk actions:      [a0 a1 a2 a3 a4 ... a49]
chunk epoch:          17 17 17 17 17 ...  17

steps:
                    a0  a1  a2  a3  a4
                    |   |   |   |   |
GIE epoch:          17  17  17  18  18
                    |   |   |   |   |
decision:          ALLOW ALLOW ALLOW BLOCK BLOCK
```

The authority check must therefore occur at the per-timestep extraction boundary.

---

## 6. H3 — Revocation Invalidates Already-Generated Actions

### Hypothesis

> `valid-at-generation != valid-at-commit`.

When a chunk is generated, its actions receive an `action_epoch` representing the authority context under which the chunk was generated/accepted.

The GIE independently maintains the current authority epoch.

The decisive condition is:

```text
if action_epoch != current_authority_epoch:
    BLOCK
```

This must apply even when the action remains cached in `current_action_chunk`.

A revoked authority therefore invalidates already-generated but not-yet-consumed actions.

### Epoch ownership

The scheduler should remain generic.

- `action_epoch` is metadata associated with the accepted chunk, preferably per environment because the scheduler state is per environment.
- `current_authority_epoch` is owned by the external GIE / authority provider.
- The scheduler does not interpret governance semantics.
- Authority is queried at each action-consumption step.

On environment reset, stale chunk metadata must be invalidated together with the chunk/index state.

A monotonically advancing epoch or equivalent non-reusable authority context should be used so that an old authorization cannot become valid merely because an integer value is reused.

---

## 7. H4 — GR00T Remains Unchanged

### Hypothesis

> GR00T is unaware of enforcement.

The policy continues to request/generate action chunks regardless of whether GIE permits their execution.

The intended architecture is therefore:

```text
                 +----------------+
                 |   GR00T N1.x   |
                 | autonomous VLA |
                 +-------+--------+
                         |
                    action chunk
                         |
                         v
              +---------------------+
              | Action Chunk        |
              | Scheduler            |
              +----------+----------+
                         |
                  timestep action
                         |
                         v
              +---------------------+
              |        GIE          |
              | authority check    |
              +----+-----------+----+
                   |           |
                 ALLOW        BLOCK
                   |           |
                   |       hold_action
                   |           |
                   +-----+-----+
                         |
                         v
                     env.step()
                         |
                         v
                  G1 WBC / Pink
                         |
                         v
                       PhysX
```

No GR00T model, policy-server protocol, or inference logic needs to be modified for the first experiment.

---

## 8. BLOCK Semantics — Hold Action

The existing `Gr00tRemoteClosedloopPolicy` already derives a `hold_action` from the current `robot_joint_pos` using the relevant joint-name mapping.

This provides an existing action-space-compatible representation of the current pose.

For the v0.1 experiment:

```text
BLOCK → hold_action
```

This is preferred over a zero tensor.

### Rationale

A zero action may represent a large or otherwise unintended command depending on the embodiment action space. Holding the current pose minimizes the additional control disturbance introduced by the enforcement mechanism itself.

An explicit safe target / stand-still pose remains a later alternative if simulation results show that current-pose holding is insufficient.

---

## 9. Scheduler Lifetime Semantics

The relevant scheduler state is per environment.

During chunk replay:

```text
current_action_index = 0 ... action_chunk_length - 1
```

After the chunk is consumed, the scheduler marks the environment as requiring a new chunk and invalidates the active index.

On `reset(env_ids)`, the active chunk/index state is cleared and the selected environments require a new chunk.

The authority metadata must follow the same lifetime semantics as the cached chunk. A reset must not permit a stale action epoch to survive into a new episode.

---

## 10. Minimal GIE Interface

The first experiment should keep GIE independent of GR00T and Isaac Lab.

A minimal conceptual interface is:

```python
class GIE:
    def check(
        self,
        env_id: int,
        action: Tensor,
        action_epoch: int,
        authority_context: AuthorityContext,
    ) -> Decision:
        # Decision = ALLOW | BLOCK + reason
        ...
```

The interface is intentionally generic.

The GIE should not require knowledge of GR00T internals, the action scheduler implementation, or G1 controller semantics beyond the execution contract supplied by the integration layer.

## 11. Metrics and Evidence

The experiment should record at minimum:

| Field | Meaning |
|---|---|
| `env_id` | Vectorized simulation environment |
| `sim_step` | Simulation/control step |
| `chunk_index` | Action index within the active chunk |
| `action_epoch` | Epoch associated with the generated/accepted action |
| `current_authority_epoch` | Epoch observed at commit decision time |
| `decision` | `ALLOW` or `BLOCK` |
| `block_reason` | e.g. `epoch_mismatch`, `revoked`, `expired` |
| `GR00T_inference_continues` | Confirms policy remains active after BLOCK |
| `safe_action_emitted` | Indicates hold/safe replacement was emitted |
| `unauthorized_action_forwarded` | Must remain false |

For stronger evidence, record an action digest for the intended policy action and, when BLOCK occurs, the digest of the replacement action.

Conceptually:

```text
intended_action_digest
        |
        +-- action_epoch
        +-- current_authority_epoch
        +-- decision
        +-- block_reason
        +-- replacement_action_digest
        +-- env_id
        +-- sim_step
```

This creates a directly correlatable execution-authority evidence record and is compatible with the broader EABC/SIF evidence-correlation model.

## 12. Leakage vs. Residual Physical Effect

The experiment must distinguish two different phenomena.

### Execution leakage

An unauthorized GR00T action crosses the enforcement boundary and reaches the downstream controller / actuator path.

This is a **FAIL**.

### Residual physical/simulation effect

After the last authorized action, the simulated humanoid may continue to exhibit:

- non-zero joint velocity;
- momentum;
- contact forces;
- center-of-mass movement;
- other physical dynamics.

This is **not automatically execution leakage**.

The first experiment therefore evaluates both, but only unauthorized command propagation constitutes an enforcement failure.

---

## 13. PASS / FAIL Criteria

### FAIL if any of the following occurs

1. An action with `action_epoch != current_authority_epoch` reaches the downstream execution path as the intended GR00T action.
2. A revoked cached action is forwarded after authority revocation.
3. The enforcement decision is made only at chunk fetch rather than per consumed action.
4. GR00T must be stopped, modified, or made governance-aware in order to enforce the block.
5. A reset allows stale action/authority metadata to remain executable.

### PASS if all of the following hold

1. Authorized actions execute normally before revocation.
2. Authority revocation takes effect without modifying GR00T.
3. Already-generated actions from the revoked epoch are blocked when subsequently consumed.
4. A safe/hold action is used as the BLOCK replacement.
5. No unauthorized GR00T action reaches the downstream execution path.
6. GR00T inference continues independently of the enforcement decision.

---

## 14. Implementation Boundary

The first implementation should make the smallest possible change to the existing stack:

```text
1. GR00T remains unchanged.
2. Scheduler semantics remain unchanged except for the enforcement hook/adapter.
3. GIE remains an external component.
4. action_epoch is attached to accepted chunk metadata.
5. GIE.check() runs for every consumed timestep action.
6. BLOCK substitutes the existing hold_action.
7. Instrument the boundary before downstream execution.
```

The preferred implementation form is a thin enforcement layer around the scheduler rather than embedding governance policy into GR00T or the G1 embodiment controller.

The exact code-level mechanism for associating `action_epoch` with the scheduler's cached chunk remains an implementation detail to be selected after the final source inspection.

---

## 15. VERIFIED / INFERRED / OPEN

### VERIFIED

- `policy_runner.rollout_policy()` obtains actions through `policy.get_action(env, obs)`.
- `Gr00tRemoteClosedloopPolicy.get_action()` obtains/fetches a GR00T action chunk and delegates timestep selection to its action scheduling state.
- The scheduler extracts one action from the cached chunk using the current per-environment action index.
- `env.step(actions)` receives the scheduler result directly from the rollout loop.
- An existing `hold_action` is derived from current robot joint positions.
- The G1 downstream path includes embodiment-specific WBC/Pink processing and ultimately `set_joint_position_target(...)`.
- Scheduler state and reset semantics are maintained per environment.

### INFERRED / ARCHITECTURAL DECISION

- Point B is the preferred GIE enforcement location.
- Per-action authority evaluation is required to satisfy H2/H3.
- `action_epoch` should follow the lifetime of the accepted cached chunk.
- Current authority should be evaluated at action consumption time rather than cached with the chunk.
- Existing `hold_action` is the preferred v0.1 BLOCK replacement.

### OPEN

- Exact code-level mechanism for attaching `action_epoch` without coupling governance semantics into the generic scheduler.
- Exact G1 action tensor semantics for every supported action term/configuration.
- Exact instrumentation location needed to independently prove that the intended unauthorized action did not reach the WBC/PhysX boundary.
- Whether an explicit stand-still target should replace current-pose hold after initial simulation results.

---

## 16. Next Experimental Step

The next step is **implementation of the minimal GIE enforcement prototype**, not further architectural expansion.

The first test should exercise the decisive sequence:

```text
Authority epoch 17
        |
        +-- GR00T generates chunk epoch 17
        |
        +-- actions 0..N execute → ALLOW
        |
        +-- authority revoked → epoch 18
        |
        +-- remaining epoch-17 actions → BLOCK
        |
        +-- hold_action emitted
        |
        +-- GR00T continues inference
        |
        +-- unauthorized GR00T actions forwarded = 0
```

This experiment isolates the core claim:

> **Autonomous action generation does not imply execution authority.**

Only after this baseline is demonstrated should the independent Halos/HOISA safety decision be added as the second authorization axis.
